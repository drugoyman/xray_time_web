# Проброс через CRM: предложение, не применено

Запрос владельца 27.10.2026: возможен ли доступ WireGuard, Hiddify и других
клиентов к VPN через сервер CRM. Этот документ описывает схему; правила NAT
и firewall пока не добавлялись.

```text
Приложение → CRM 217.18.60.102 → VPN 89.19.209.17 → интернет
```

## Проверенные предпосылки, 27.10, 10:11 МСК

- С CRM уже проверены ping, TLS и реальная передача VLESS на оба IP VPN.
- На CRM включён net.ipv4.ip_forward=1.
- CRM/входы используют TCP 80, 443, 8443 и UDP 443, 8443; занимать их нельзя.
- TCP 14443 и UDP 51820 среди прослушиваемых портов не обнаружены.
- В FORWARD политика DROP и цепочки Docker; одного DNAT будет недостаточно.
- Существующий NAT обслуживает Docker, его правила нельзя затирать.

## Предлагаемые соответствия

| Вход на CRM | Назначение на VPN | Назначение |
|---|---|---|
| TCP 14443 | 89.19.209.17:443 | VLESS TCP TLS, Hiddify/Streisand и совместимые клиенты |
| UDP 51820 | 89.19.209.17:51820 | Системный WireGuard wg0 |
| Отдельные согласованные порты | Соответствующие inbounds Xray | Другие протоколы после сверки конфликтов |

Реализация: ограниченные конкретными IP, портами и протоколами DNAT + SNAT,
добавочные разрешения FORWARD и отслеживание обратных соединений.
SNAT нужен, чтобы ответы VPN возвращались через CRM, а не шли напрямую клиенту.
Глобальную политику FORWARD и существующие цепочки Docker менять не требуется.

## Изменения в приложениях

- Hiddify/Streisand: адрес сервера 217.18.60.102, TCP-порт 14443,
  TLS SNI yugoo.su; UUID и параметры протокола сохраняются.
- WireGuard: Endpoint=217.18.60.102:51820; ключи и AllowedIPs сохраняются.
- Старые локально импортированные профили не обновятся автоматически.
- Домен yugoo.su не нужно переключать для проверки такого варианта.
- TLS и WireGuard завершаются на VPN, CRM пересылает зашифрованный трафик.

Поддержка приложения определяется протоколом профиля, не его названием.
При блокировке UDP в клиентской сети проброс UDP сам по себе не обеспечит
работу WireGuard. TCP-VLESS и UDP-WireGuard проверяются раздельно.

## Перед применением и после него

1. Сохранить firewall/routing snapshot и исходное состояние CRM, поставить
   ограниченный по новым правилам автоматический rollback.
2. Установить только новые правила с явными комментариями проекта; не трогать
   CRM, SSH, Docker NAT, системный WireGuard или клиентские учётные записи.
3. Проверить из проблемной сети TCP 14443, доверенный TLS и VLESS HTTP 200.
4. Проверить WireGuard новым handshake и передачей данных с реального клиента.
   UDP-проба без WireGuard-клиента не подтверждает handshake.
5. Проверить CRM healthz и существующие входы 443/8443 до/после.
6. После успеха сохранить правила для загрузки, проверить восстановление
   правил при перезапуске Docker и отменить временный rollback.

Весь VPN-трафик такого входа пойдёт через канал и ресурсы CRM. Доступ будет
зависеть от двух серверов; для длительной нагрузки стоит оценить отдельный relay.
