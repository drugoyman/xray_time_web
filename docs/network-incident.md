# Инцидент прямого доступа, 26–27.10.2026

## Наблюдения

- Из проблемной сети напрямую не устанавливаются TCP-соединения к
  89.19.210.13:22, :443 и :4200.
- Проверки обычного интернета успешны.
- На Windows включён системный прокси Hiddify. HTTP-запрос через системный прокси
  и сырой TCP-сокет имеют разные пути и разные внешние IP.
- Через существующий SOCKS-прокси удалось подключиться к SSH сервера.
- С внешних Check-Host узлов ping и TCP 22/443 успешны.
- Сервер пингует фактический публичный IP проблемной сети: 3/3 ответа, около 65 мс.
- Контрольный захват на eth0 сервера одновременно видит 3 исходящих ICMP и
  3 ответа; при прямых попытках к 22/443/4200 входящих TCP от этого IP — 0.
- На 26.10 у host firewall политика INPUT ACCEPT, блокировки проблемного IP не
  обнаружены. 27.10 установленный позднее host Fail2ban этого IP не банит.
- TLS на самом сервере успешен и через loopback, и через его публичный адрес.
  Сертификат и приватный ключ имеют совпадающий публичный ключ.
- Аккаунт из последнего проверенного QR авторизуется и получает HTTP 200 через
  VLESS, доставленный по SSH-туннелю. Это проверка сервера, не сети iPhone.
- Через текущий Hiddify SOCKS TCP 443 открывался, но TLS завершался EOF.
  Этот отдельный симптом не объяснён: возможны правила прокси или фильтрация пути.

Локальный исходный публичный IP и сведения о клиентах намеренно не публикуются.

## Что установлено и что остаётся гипотезой

Проблема прямого соединения возникает **до сетевого интерфейса сервера**.
Данных недостаточно, чтобы назвать конкретный фильтрующий узел или организацию.
Проверки не исключают шлюз/защиту локальной сети, путь оператора и внешнюю защиту
хостинга. Одного отсутствия пакетов на сервере недостаточно для обвинения провайдера.

Изначальный вывод «сервер недоступен целиком» был слишком широким и исправлен
после независимых внешних проверок. Серверные сервисы и путь конкретного клиента
должны проверяться отдельно.

## Трассировки

С сервера до 194.33.23.97 адрес достигнут:

```text
1  5.44.46.1         2 мс
2  10.66.34.1       27 мс
3  *
4  10.255.1.137      3 мс
5  94.228.119.216   40 мс
6  193.106.112.152  59 мс
7  86.62.12.209     65 мс
8  194.33.23.97     62 мс
```

Позже пользователь уточнил: 194.33.23.97 не является фактическим внешним IP
проблемного подключения. Поэтому эта трасса не доказывает обратный доступ к нему.
Трасса к фактическому клиентскому адресу дала ответы транзитных узлов; проверка
была ограничена 20 hops, а отдельный ping до адреса успешен.

С Windows ICMP traceroute показал локальный шлюз и далее `*`; это не локализует сбой.

## Следующие проверки

1. Проверить выходящие SYN на WAN локального шлюза в момент прямого подключения.
2. Если SYN выходят, сопоставить одновременные захваты с хостингом/оператором.
3. Для iPhone отдельно сравнить Wi-Fi и мобильную сеть и получить журнал Streisand.
4. При наличии второго IP сначала проверить доступ с проблемной сети, затем
   решать вопрос переноса DNS и профилей. Смена IP не гарантирует устранение сбоя.
