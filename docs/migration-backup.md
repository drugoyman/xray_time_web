Каталог закрыт от наследуемых разрешений: полный доступ имеют текущий

## Состав

- `vpn-server.tar.gz`: проект `/root/3x-ui`, согласованный снимок основной SQLite
  базы, сертификаты, `/etc/wireguard`, конфигурация обслуживания и таймеров,
  Docker/Fail2ban/sysctl, имеющиеся настройки сети, cron и обновления сертификатов.
- Внутри этого архива `vpn/docker-image.tar.gz` содержит экспорт фактического
  Docker-образа; `vpn/snapshot` — inspect контейнера и образа, runtime Xray,
  текущие правила firewall, адреса/маршруты, пакеты, службы и рабочий WG-конфиг.
- `vpn/MANIFEST.json`: SHA256 обычных файлов, результат integrity_check,
  количество записей основных таблиц, ID образа и отсутствовавшие необязательные пути.
- `crm-relay.tar.gz`: действующий скрипт проброса, systemd unit, снимок firewall
  и результат проверки CRM. Код приложения CRM и его база сюда не входят.
- `project.bundle` и `project-source.zip`: история Git и отслеживаемые исходники
  проекта администрирования на момент завершения копии.
- `verification.json`, `SHA256SUMS.txt`, `RESTORE.md`: результаты проверки,
  контрольные суммы локальных файлов и инструкция переноса.

Копия не является образом всего диска. Исторические резервные копии и журналы,
ключи SSH хоста, пароль root и пользовательские файлы вне указанных каталогов
не экспортируются. Новый сервер получает собственный административный доступ.
Статистика в момент снимка продолжает меняться; пользователи не отключаются.

## Подготовка нового сервера

1. Использовать совместимый Linux и архитектуру из `os-release.txt` и
   `docker-images.json`. Установить Docker с Compose, WireGuard, Python 3,
   firewall-инструменты и зависимости по сохранённому списку пакетов.
2. Проверить SHA256 архивов по `SHA256SUMS.txt`, распаковать в отдельный каталог,
   доступный только root. Сверить `MANIFEST.json` перед восстановлением.
3. Загрузить сохранённый образ через `gzip -dc vpn/docker-image.tar.gz | docker load`.
   Экспорт по ID может загрузить образ без тега. Сверить ID, затем присвоить ему
   точное имя/digest-совместимую ссылку, которую будет использовать Compose;
   при необходимости указать сохранённый `sha256:…` как `image` в копии Compose.
   Не загружать произвольный latest вместо проверенного образа.
4. Восстановить `/root/3x-ui` и каталоги сертификатов из `vpn/files`, сохранив
   владельцев и права. Основная база уже находится по исходному пути проекта.
   Сопоставить bind mounts с `docker-inspect.json`, особенно сертификат панели.
5. Подготовить WG из `/etc/wireguard`. Сверить постоянный конфиг с
   `snapshot/wg-live.conf`: рабочие peers могут отличаться от сохранённых.
   Сохранение серверных/клиентских ключей позволяет использовать прежние аккаунты.
6. Настроить forwarding, NAT и разрешённые порты под интерфейс и IP нового хоста.
   Проверить слушающие порты по `listeners.txt` и inbounds в базе. Подключения
   Xray и системный WireGuard могут использовать разные порты и правила.
7. Установить нужные скрипты обслуживания и systemd units, проверить пути,
   зависимости и сертификаты. Таймер offsite не включать автоматически:
   ремонт Google Drive ранее остановлен владельцем.

Не заменять вслепую `/etc/netplan`, `/etc/network`, firewall, systemd и настройки
Docker на новом сервере. Снимки описывают старый хост; применение целиком может
оборвать SSH или конфликтовать с сетью провайдера. Настройки сети сверять также
с фактическими `addresses.json` и `routes.json`, поскольку старые файлы могут
содержать уже удалённый дополнительный IP.

## Переключение и проверка

1. Запустить контейнер и WG на новом сервере после адаптации конфигурации.
   Проверить SQLite integrity, доступ к панели, валидность TLS и время сервера.
2. Выполнить полноценный запрос HTTPS через VLESS и handshake с передачей
   данных через WG. Проверка открытого порта не заменяет эти проверки.
3. При сохранении входа через CRM поменять backend в копии relay-скрипта на
   новый VPN IP, предварительно сохранив правила и предусмотрев откат. Сверить
   все фактические mappings скрипта, включая дополнительные UDP-порты.
   Проверить CRM health до/после; при необходимости удалить только конкретные
   старые conntrack-состояния relay, не очищая общую таблицу.
4. Для прямых клиентов обновить адрес сервера/Endpoint. Ссылки с IP сами не
   изменятся. SNI должен соответствовать сертификату. При переносе доменного
   входа обновить DNS и проверить выпуск/продление сертификатов.
5. До отключения старого сервера сделать финальный согласованный снимок базы
   и конфигов: эта копия фиксирует состояние 29.10.2026. Оставить старый сервер
   доступным для отката до подтверждения клиентов из нужных сетей.

Распаковка, загрузка образа и запуск на новом сервере в рамках создания копии
не выполняются. Проверка архива подтверждает целостность, но не заменяет
контрольное восстановление и тест VPN на целевом хосте.
